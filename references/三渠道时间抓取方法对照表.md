# 三渠道时间抓取方法对照表

> 口径：只讨论筛选流程已冻结后，三渠道各自能拿到的**源头时间**。筛选流程不动，仅研究时间层。

## 一、三渠道时间字段对照

| 渠道 | 建页期（最早信号） | 源头开始时间 | 源头结束时间 | 最后更新时间 |
|---|---|---|---|---|
| **好游快爆** | **URL slug 内嵌日期**：形如 `https://act.3839.com/n/hykb_hd/{prefix}{YYYYMMDD}{suffix}/index.php`，例如 `osgame20260902a437` → 建页期 **2026-09-02**。**无需联网**，直接读 URL 即可。<br><br>⚠️ 例外：老式 `huodong3.3839.com/.../yxss.php?comm_id=13` 这类 `comm_id` URL 没有 slug 日期，目前 25 款里有 2 条（洛克王国逐锋杯、最强爆友）真查不到。 | **活动详情页中文"活动时间"文本解析**；快爆 H5 无结构化时间字段，只能抓页面后正则/锚点提取。例如页面写"9月10日10点开启"就解析为该时刻。 | 同上，从详情页"活动时间"区间一起解析结束时间。 | **无**。快爆数据层不暴露 `utime` 或类似"最后更新"字段。 |
| **4399游戏盒** | **URL 本身无建页期**；但可用 **API `stime` 代理**：`mapi.yxhapi.com` 列表接口返回的 `stime` 是该活动在 4399 后台的**上线/建活动时间**，功能上等同于"建页期"。**需要联网**调用 API。 | **API 原生字段 `stime`**：Unix 秒级时间戳；即 4399 后台配置的开始时间。注意：它通常比页面规则写的"真正开始时间"早 0~16 天。 | **API 原生字段 `etime`**：Unix 秒级时间戳；惯例写成 23:55:00，代表后台配置的结束时间。 | **API 原生字段 `utime`**：Unix 秒级时间戳；代表该条活动记录在 4399 后台的**最后更新时间**，纯粹元数据，**不是**开放领取/可参与时间。 |
| **OPPO游戏中心** | **URL 本身无建页期**，目前也未抓到任何创建/发布时间戳；能拿到的最早时间就是活动开始时间。 | **情况 A（nvwa 动态站，57/147 行）**：API 卡片 `startTime/endTime` **实测几乎全为空**（全部 147 行 OPPO 活动里真实 API 卡片时间 = 0 条）；可靠时间 100% 来自 nvwa 活动页 `schema.js` 的 `timeRange.start`（文本 `YYYY-MM-DD HH:MM:SS`，**可达秒级**）。**注意：这不是"兜底"，schema.js timeRange 就是 OPPO 真正的源头开始时间。**<br><br>**情况 B（staticActivity 静态页，90/147 行）**：无 API 卡片时间（静态页本就不在 nvwa 卡片系统里）；只能从静态 HTML 页面内自标注的"活动时间：X月X日-X月X日"文本提取（精度低、常缺失）。 | 同"源头开始"逻辑，取对应字段的结束值（情况 A 取 timeRange.end；情况 B 取页面文本区间）。 | **无**。OPPO 数据层不暴露创建/更新字段；且 API 卡片本身就不返回时间（与是否结束无关）。 |

## 二、OPPO 为什么"有的有 API 卡片时间、有的没有"——已纠正

⚠️ **重要更正**：上轮给的表把"schema.js 兜底时间"误标成了"API 卡片时间"，导致误以为"有些 OPPO 活动有 API 卡片时间、有些没有"。**2026-09-12 18:40 现场实测：全部 147 行 OPPO 活动里，真实 API 卡片时间 = 0 条**——OPPO 的详情接口卡片几乎从不携带 `startTime/endTime` 毫秒字段。

所以"有没有 API 卡片时间"根本不是一个有效维度。OPPO 时间的真实分布是：

| 现象 | 根因 | 还能不能拿到时间 |
|---|---|---|
| URL 里有 `nvwa-static/sites/...` | nvwa 动态站，API 卡片**不返回时间**（与是否进行中无关）；时间写在活动页 `schema.js` 的 `timeRange` 里 | 能（从 nvwa schema.js，精度到秒） |
| URL 是 `ie-activity/staticActivity/...` | 静态 HTML 页，本就不在 nvwa 卡片系统；时间只能从页面自标注文本提取 | 部分能（页面文本常缺失/只有日粒度） |

> **结论修正**：你之前判断"OPPO 没结束的活动能抓到 API 卡片时间、已结束的抓不到"——这个结论不成立，因为它建立在误标数据上。真实情况是：**OPPO 可靠时间源 = nvwa 站点的 schema.js timeRange**；staticActivity 站点的时间最不可靠（页面文本，常缺）。API 卡片时间基本可视为不可用。
>
> 顺带说明：你观察到的"无 API 开始时间的都是噪音活动"也**不成立**——57 个 nvwa 站全部"无 API 卡片时间"，其中就包含真奖励（如部落冲突 14 周年 Q币、金铲铲五周年手机等）。判断真/假奖励要看奖励分类（Q币/现金/实体），不是看有没有 API 卡片时间。

## 三、关于"好游快爆从建页期开始抓，建页期结束再抓一次"

这个逻辑需要修正一下：

- **建页期不是"一段时间"，而是一个日期点**。它是快爆 URL slug 里内嵌的 `YYYYMMDD`，代表这个 H5 页面在快爆后台被创建的日期。
- 页面一创建，我们就可以"发现"这个活动，但此时活动通常**还没真正开始**（比如 slug 日期 9 月 2 日，实际活动 9 月 10 日开启）。
- 因此正确的用法是：
  1. **用建页期做"最早发现信号"**：slug 日期一出现，就知道有这个活动了；
  2. **在详情页解析真正的"活动时间"**：这才是源头开始/结束；
  3. 不需要等"建页期结束"——建页期是点，没有"结束"概念。应该是**建页期出现后就持续监控/解析详情页时间**，直到页面公布真实活动时间。

简单记：**建页期 = 页面出生证明，不是活动开始时间**。

## 四、能否做成"雷达网站"让 VS Code / 自动化自动抓 4399 时间

**可以**。4399 API 是公开 HTTP 接口（`mapi.yxhapi.com`），只要环境能联网就能抓。常见架构：

| 层级 | 实现方式 | 说明 |
|---|---|---|
| 采集层 | Python 脚本定时调用 4399 API | 用 `requests`/`httpx` 请求 `mapi.yxhapi.com`，解析 `stime/etime/utime`。 |
| 调度层 | 本地 cron / 本环境 automation / VS Code Task | 例如每 2 小时跑一次 `python 4399_sept_crawl_v2.py`。 |
| 存储层 | SQLite / JSON / 本地文件 | 把每次结果落库，方便对比历史。 |
| 展示层 | 静态 HTML + JS 表格 / Flask / FastAPI | 用本地浏览器或 VS Code 预览打开，刷新即看最新。 |

> 注意：4399 可能有频率限制或反爬；实际跑的时候要加请求间隔、失败重试、User-Agent 伪装。

**最轻量的做法**：直接在本环境设一个 `automation_update` 定时任务，每 N 小时自动跑 `run_all_channels.py`（三渠道一起），生成最新对照表；你在浏览器里打开生成的 HTML/markdown 即可，就是个"雷达"看板。

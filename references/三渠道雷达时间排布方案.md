# 三渠道雷达时间排布方案

> 目标：用"雷达"思路把三渠道活动时间串成一条时间线，既让你**提前知道活动存在**（后台创建/建页期），又能在**活动开始那一刻提醒你参与**（页面公布开始时间）。
> 
> 口径：筛选流程已冻结，本方案只讨论"时间层如何排布"，不改分类逻辑。

---

## 一、三渠道各自能拿到的时间信号

| 渠道 | 最早信号（发现期） | 准备信号 | 参与信号（开抢期） | 结束信号 |
|---|---|---|---|---|
| **好游快爆** | **URL slug 建页期**<br>无需联网，从 URL 读 `YYYYMMDD`<br>例如 `osgame20260902a437` → 2026-09-02 建页 | 页面已上线，但详情页写的"活动时间"还没到 start | **详情页"活动时间" start**<br>例如"9月10日10点开启" | 详情页"活动时间" end |
| **4399游戏盒** | **API `stime` 后台上线时间**<br>需联网调 `mapi.yxhapi.com`<br>普遍比页面开始早 1~16 天 | `stime` 已出，页面规则时间未开始 | **页面规则活动时间 start**<br>（通常与 `stime` 同日或晚几天） | API `etime` / 页面规则 end |
| **OPPO游戏中心** | **无**<br>URL 无日期，API 卡片不返时间，后台创建时间目前抓不到 | 无 | **nvwa 站 schema.js `timeRange.start`**<br>页面一上线即可抓，秒级精度 | schema.js `timeRange.end` |

---

## 二、雷达时间轴如何排布

把每个活动抽象成 **3 个关键节点**：

```
[T0 发现] ──→ [T1 准备] ──→ [T2 开抢] ──→ [T3 结束]
```

### 节点定义

| 节点 | 含义 | 你收到什么提醒 | 各渠道取值 |
|---|---|---|---|
| **T0 发现** | 活动刚被创建/建页，你还不能参加，但已经可以知道"有这么个活动" | "XX游戏在XX渠道出现了新活动，先关注着" | 快爆=slug建页期；4399=API stime；OPPO=无（只能从 T2 开始） |
| **T1 准备** | 活动页面已公布规则，但开始时间还没到 | "XX活动将于 YYYY-MM-DD HH:MM 开始，设好闹钟" | 快爆=详情页活动时间 start；4399=页面规则活动时间 start；OPPO=schema.js timeRange.start |
| **T2 开抢** | 活动正式开始，可以立即参与 | "XX活动已开启，立即参与" | 快爆=详情页活动时间 start；4399=页面规则活动时间 start；OPPO=schema.js timeRange.start |
| **T3 结束** | 活动截止 | "XX活动即将结束/已结束" | 快爆=详情页 end；4399=etime/页面 end；OPPO=schema.js timeRange.end |

> 说明：对快爆/4399/OPPO 的多数活动，**T1 和 T2 是同一个时间点**——页面公布的开始时间就是你能参与的时间。T0 则是更早的"预告"信号。

## 三、雷达看板怎么呈现

建议看板按**活动维度**一行，按**时间维度**多列，并带上"倒计时"状态：

| 游戏 | 渠道 | T0 发现时间 | T1/T2 开始时间 | T3 结束时间 | 当前状态 | 操作 |
|---|---|---|---|---|---|---|
| 王者万象棋 | 快爆 | 09-02（建页） | 09-10 07:00 | 10-10 23:59 | 距开始 3 小时 | 设提醒 |
| CODM×崩坏3 | 4399 | 08-25 11:15（stime） | 09-10 00:00 | 11-09 23:55 | 进行中 | 打开链接 |
| 和平精英 | OPPO | — | 09-10 00:00 | 09-23 23:59 | 进行中 | 打开链接 |

### 状态自动流转

1. **未公布开始时间**（只有 T0，还没有 T1/T2）→ 状态："待公布"，只展示发现时间和来源链接。
2. **已公布开始时间，但还没到** → 状态："准备中（距开始 X 天 X 小时）"，可设提醒。
3. **已开始、未结束** → 状态："进行中"，置顶显示，提醒"立即参与"。
4. **已结束** → 状态："已结束"，可折叠或标灰（但仍保留用于复盘）。

## 四、三渠道采集节奏建议

不同渠道的"最早信号"出现时机不同，雷达采集频率也应不同：

| 渠道 | 采集目标 | 建议频率 | 原因 |
|---|---|---|---|
| **好游快爆** | ① 发现新 slug（T0）<br>② 解析详情页活动时间（T1/T2） | **每 6~12 小时** | slug 一建页就能发现；详情页规则可能提前几天到几小时更新 |
| **4399游戏盒** | ① API 列表取 stime（T0）<br>② 详情页规则时间（T1/T2） | **每 2~6 小时** | API 稳定，可高频扫；stime 一更新就知道 |
| **OPPO游戏中心** | ① 发现新活动链接<br>② schema.js timeRange（T1/T2/T3） | **每 6~12 小时** | 没有 T0，只能等活动页发布；timeRange 稳定后不再变 |

> 采集层只负责"拿到所有信号"；排布层负责把同一活动在不同渠道的多个时间拼成一条时间线。

## 五、你要拍板的一个关键问题

**表内时间到底写哪个？**

| 方案 | 写 T0（最早发现） | 写 T2（页面开始） | 优缺点 |
|---|---|---|---|
| A | 快爆 slug / 4399 stime / OPPO — | 详情页 start / 页面规则 start / schema.js start | **双时间都要**，看板最完整，但表会变宽 |
| B | 不写 T0，只写 T2 | 详情页 start / 页面规则 start / schema.js start | 表最简洁，但会丢失"提前准备"信息 |
| C（当前） | 表内只保留一个"活动时间"字段 | 默认写 T2 | 最符合用户直觉，但需要另一个字段单独存 T0 |

**我的建议**：采用 **方案 A 的变体**——主表保留两列：
- **发现时间**（T0）：快爆 slug 日期 / 4399 stime / OPPO 空
- **开始时间**（T2）：三渠道统一的"可以参与的时间"

这样你既能提前做准备，又不会把"后台上线"和"真正能参加"搞混。

## 五、25 个游戏如何分布（看板布局原则）

25 游戏 × 3 渠道 ≈ 79 条活动，不能平铺成一张长表。采用**三层折叠**：

1. **第一层：按状态分组（雷达灵魂）**
   - 顶部三个 tab：`进行中`（绿，置顶）/ `准备中`（橙，带"距开始 X 天"倒计时）/ `已结束`（灰，默认折叠）。
   - 每天只看"进行中 + 准备中"，过期活动不打扰。

2. **第二层：游戏聚合（25 个不展开）**
   - 25 个游戏做成筛选 chip 横排；默认全展开但每张卡只显示"游戏名 + 状态徽章"。
   - 点某游戏 chip → 下钻只看该游戏在 3 渠道的活动。
   - 不点时所有游戏并排成卡片流，每张卡高度固定（游戏名 + 3 渠道一行时间轴）。

3. **第三层：渠道并排（每张卡内部）**
   - 每张游戏卡内，3 渠道各一行，统一格式：
     ```
     好游快爆  T0 建页 09-02 → T2 开抢 09-10 07:00
     4399      T0 stime 09-09 → T2 开抢 09-10 00:00
     OPPO      无 T0         → T2 开抢 09-10 00:00
     ```
   - 一眼看出：哪个渠道更早提醒（T0）、哪个渠道开始最早（T2）。

> 分布好处：状态优先 = 每天只看该行动的；游戏聚合 = 想看哪个点哪个；渠道并排 = 同活动 3 渠道时间差一目了然。

## 六、最小可行雷达实现

如果你现在就想跑起来，最小步骤：

1. **数据源**：复用已有的三个脚本（`hykb_web_sept_crawl_v2.py`、`4399_sept_crawl_v2.py`、`oppo_sept_crawl_v2.py`）。
2. **提取 T0/T2**：
   - 快爆：URL 正则取 slug 日期 → T0；详情页 `parse_times_v2` → T2。
   - 4399：API `stime` → T0；页面规则时间 / `etime` → T2/T3。
   - OPPO：`schema.js timeRange` → T2/T3；T0 留空。
3. **生成看板**：写一个小脚本把结果渲染成 HTML 表格，按"进行中 / 准备中 / 已结束"分组，带倒计时。
4. **定时刷新**：用 `automation_update` 每 6 小时跑一遍，浏览器打开 HTML 即可。
